## Diff against stock sdpa_decode

The stock `sdpa_decode/` and `sdpa/` directories are byte-identical to v0.78.0 (`git diff --stat` lists nothing under them), so the baseline/stock rows are unaffected by the kernel work. Behavioural differences of the Palu op beyond the K/V rebuild itself:

1. **`use_half_tile` forced false** (`K/device/palu_sdpa_decode_program_factory.cpp:558`; stock: `is_causal && num_q_heads <= 16 && bf16`). Q, mask, statistics and intermediates are full 32-row tiles. Numerically equivalent (padded rows are independent), costs time; the results docs acknowledge it (stage2.md §3).
2. **`c_1` holds bf16 K_rot** (factory 664, `krot_df`) where the stock K CB carries the cache dtype (bfp8). The fused path therefore attends over a *more* precise K than the naive path (which typecasts reconstructed K to `kv_cache_dtype`). Fidelity comparisons fused-vs-naive are not at equal K precision; the direction favours the fused op.
3. **Zero tile (`c_12`) no longer produced** by the writer; `DYNAMIC_CHUNK_SIZE` is a compile `#error` (compute 128-130). The wrapper always resolves a nonzero chunk so the dynamic path is unreachable; the mask-fusion branch of `matmul_blocks` (`add_mask`) is passed `false` everywhere.
4. **Default chunk** (`K/palu_sdpa_decode.cpp:96-100`): lowered to 128 when `r_k > 128` or `u_v` is given, unless the caller pins one. Stock picks the largest power of two dividing S (cap 512); `palu_get_chunk_size` is the same function.
5. **Validation narrowed** to causal, unpaged, `cur_pos_tensor`, no mask/sink/window/share_cache/page table (device_operation.cpp 477-483); `head_dim == 128` (404); `batch <= 32` (485); `r_k` logical width in 32..512 (83-89); Phase 1 `k_chunk_size <= 128` (562-566); Phase 2 requires `fp32_dest_acc_en` (556); GQA checks use `w_rot`'s head count instead of `k_shape[1]` (425-445).
6. **Work split**: unchanged for `heads_per_core` in {0,1}. With `heads_per_core > 1` the item becomes (batch, group of H heads) and the split is capped at 4 cores/item (factory 222-265); the "not both a split and several heads" fatal is lifted only in group mode (311-312).
7. **Reduction tree**: the host tree tables are identical to stock. In group mode the receive slots in `c_19` are per (head, round) and the semaphore nibble is bumped once per head (writer 278-416, factory 523-534). In the group branch the child merge uses `max_block` + 2x`sub_exp_block` + `mul_block_inplace` + `add_block_inplace` instead of `correction_block` (compute 566-590); the per-head branch keeps `correction_block` (compute 947).
8. **Mask / causal / cur_pos**: unchanged (`generate_mask` into `c_3`, applied once on the last chunk by the `do_reduce` core, never popped; `cur_pos` from `c_15`/`c_8`; `-1` skips the user). Group branch applies the same mask per head with `add_block_inplace<false>` (compute 379-382).
9. **Sharded inputs**: Q may be HEIGHT_SHARDED (production is: the RoPE'd Q from `rotary_embedding_llama` decode mode is L1-sharded), K/V must be DRAM (stock rule). Sharded output is still accepted by validate but no test or caller uses it. The `q_locally_available` / column-major indexing branch is inherited but unreachable in the envelope (`q_heads_parallel_factor` resolves to 1).
10. **Paged path**: `static_assert(!is_paged_attention)` in the reader (89); validate rejects a page table. Dead code retained in the reader (399-450).
11. **Reader multicast args** (`do_k_mcast`, `mcast_x/y0/y1`, `num_dests`) are repurposed for the Phase 2 table multicast; a fatal forbids combining with column-major indexing and with sub-core grids (factory 1067-1076).
12. **`update_cache_device_operation.cpp`**: only widens the dtype whitelist for `FILL` when both input and cache are BFLOAT4_B. `fill_cache_multi_core_program_factory.cpp` is a reader+writer tile copy with page size from the tensor's data format (114-115); no compute kernel. Stock bfp8/bf16 rows are unaffected; the `baseline_kv4` row exists only because of this change (its `paged_update_cache` decode path is a different op, outside this audit). `tests/test_kv_cache_bfp4_device.py` checks byte equality of the filled user and untouched neighbours.

## Unasserted assumptions

Assumptions the kernels make that no host check enforces (an asserted item is listed only where the assertion is weaker than the assumption):

- **`rot_step` was built for the same chunk the op runs with** (`palu_step_q` applies whatever constants arrive in `c_14`). The host pins the chunk and builds the table from the same value (`attention.py:299-310`, tests `_fused`/`_fused_group`), but the op cannot tell; a mismatch is silently wrong for every chunk after the first. Not checkable from shapes (rot_step is `[1,1,32,256]` for any chunk).
- **`cs_tab` rows 0..c-1 are positions 0..c-1, Meta-interleaved (pair-duplicated frequencies), in the same table the query was rotated with**; **`w_rot[:, :, :, 128:] == u_k @ T`**; **`trans_mat` is the pair-swap tile**; **Q is already rotated by its position**. All content assumptions; only shapes/dtypes are asserted (device_operation.cpp 486-497, 512, 549-553).
- **`cur_pos_tensor` dtype INT32, ROW_MAJOR, one page of >= B int32s**: the INT32/ROW_MAJOR/batch checks exist only inside the `paged_attention` branch (220-236); the unpaged Palu path never runs them. The reader reads `aligned_page_size` bytes and indexes `uint32` (reader 191-211). Inherited from stock.
- **`cur_pos[b] < S`** for tensor positions (the `cur_pos < k_shape[-2]` check at 415 covers only the never-used vector form).
- **K chunk >= 64 under fp32 accumulate at batch < 32** (the known stock defect at chunk 32). Nothing asserts it; the wrapper accepts any power of two >= 32 (`K/palu_sdpa_decode.cpp:66-77`) and `attention.py:299-300` derives the default from `fused.chunk_size(max_seq_len)`, which returns 32 for e.g. `max_seq_len = 2080`. Phase 2 *forces* fp32 accumulate (556). No test runs chunk 32 or 64.
- **`num_q_heads / num_kv_heads` is a power of two** (writer comment 429-430; partial-tile row writes assume it). Only 16/4 is ever used or tested.
- **User-pinned `k_chunk_size <= 512`**: not asserted; larger values fail loudly at CB allocation.
- **The 8x8 grid** hard-coded in `attention.py:307`; a harvested grid fails loudly in the factory (`num_cores_available <= num_cores_in_grid`).
- **`heads_per_core` layouts fill contiguous grid columns** for table multicast: asserted (factory 1084-1093).
- **Q padded rows 16..31 are finite**: not asserted; garbage rows would only affect their own (discarded) output rows.
- **`heads_per_group` in {1, 4}**: only 1 and 4 are tested for numerics (2 appears only in an envelope-rejection test).

## Findings

### [Important] The op-level reference checks at batch >= 8 are dominated by short-context rows; a kernel with the entire Phase-2 stepping missing passes them
File: `tests/test_palu_sdpa_device.py:45-56` (`_inputs`: `pos = randint(0, S)`, `pos[0]=S-1`, `pos[1:4]=0,127,128`), `:91-103` (`_check`, bars 0.99 vs fp32 reference and 0.995 vs the stock op), `:218-235`, `:262-278` (`_check_group`, same bars), `:203-205` (`test_phase2_long_context_full_batch`, the only test that walks 16 sequential chunks on one core).
What: `comp_pcc` flattens all rows. Rows with a short context have output std ~1 (attention over a few V rows), rows at full context have std ~0.02-0.06 (an average over hundreds of V rows), so the flattened PCC is carried by the short rows, which do not exercise multi-chunk logic at all. Measured with a pure-torch model of `_inputs`/`reference_decode` (`scratchpad/audit/pcc_sensitivity*.py`, seed 213919): with the test's positions at batch 32 / S 1024 / chunk 512, a kernel that never advances the query state (K rotated by `s mod chunk`) scores **0.9977** (bar 0.99, PASS); at batch 32 / S 8192 / chunk 512 (`test_phase2_long_context_full_batch`) **0.9917** (PASS); at batch 8 / S 8192 / chunk 128 (`test_grouped_latents_long_context_batch8`) **0.9979** (PASS); sin sign flipped on the 32 low-frequency pairs scores 0.9988 at 1k (PASS). With every row at full context the same defects score 0.63-0.77 and 0.80-0.95. The per-row PCC of the full-context rows in the passing cases is 0.53-0.74. For comparison the bf16-rounded-K reference scores 1.00000, so the bars are ~2 orders of magnitude looser than the achievable agreement.
Why it matters: every batch >= 8 case in `_check`/`_check_group` (11 of the ~30 reference-checked cases, including the only 16-chunk and the only full-rank 512/512 case) is close to inert for anything that only goes wrong past the first chunk or on low frequencies. Coverage of the stepping/seeding/low-frequency sign rests entirely on the batch-1 cases (`test_phase1_matches_reference[b1]`, `test_phase2_matches_reference_default_chunk[b1]`, `test_phase2_long_context` S 4096/8192, `test_grouped_latents_with_in_kernel_v[b1]`), which the same model shows do fail (0.45-0.79). The suite as a whole therefore still detects these bugs, but not where the docstrings say it does, and any path without a batch-1 full-context case (G-LRD at S >= 4096, r_k >= 128 at S >= 2048, the 512/512 layer) has no sensitive reference check.
How to verify: run `scratchpad/audit/pcc_sensitivity2.py` (CPU only); or, on the device, change `palu_step_q` to a no-op and observe which tests still pass.
Suggested fix: score PCC per batch row and take the minimum (or set all rows to `S-1` in the reference tests and keep one mixed-position test for the masking); raise the bars to what the bf16 reference actually achieves (>= 0.999 vs stock, >= 0.999 vs fp32 at batch 32); add a batch-1 full-context case to `_check_group` at S 8192 and to the 512/512 shape.

### [Important] The per-head branch still merges children with `correction_block`, which writes DST tile 4 inside a 4-tile fp32 window; the results at batch < 32 rest on measured PCC with an unexplained mechanism
File: `K/device/kernels/compute/palu_sdpa_flash_decode.cpp:947` (per-head branch), `:566-590` (group branch replacement); `sdpa/device/kernels/compute/compute_common.hpp:748-772` (`dst_reg_0..4` in one acquisition); factory `:481` (`dst_size = fp32_dest_acc_en ? 4 : 8`); `docs/results/stage2c.md` §6.1.
What: With `fp32_dest_acc_en` and `dst_full_sync_en=false` (the production and test configuration; Phase 2 requires fp32 accumulate) the math thread's DST half holds 4 fp32 tiles; `correction_block` stages five. The group branch demonstrably returned the local max as the merged max (PCC 0.334) and was fixed with primitives; the per-head branch keeps the helper because it "survives the same window in every configuration measured". The stage 2c text calls `dst_size` "a host-side constant, not the hardware DST limit"; on Wormhole in half-sync fp32 mode four tiles *is* the per-thread window, so the write to `dst_reg_4` lands in the packer's half and its safety is a timing property, not a guarantee. The stock op has the identical code, so stock rows at batch < 32 share the exposure.
Why it matters: every fused per-head number at batch < 32 (the `_b1/_b4/_b8/_b16` bench rows, `decode_check` at batch 1, the batch-8 G-LRD rows where the selector picks H=1) goes through this merge. The only evidence is PCC 0.99998 (batch 8) / 0.99935 (batch 1) against fp32 in `test_per_head_reduction_is_accurate_under_fp32_dest_acc` (`tests/test_palu_sdpa_device.py:506-522`, bar 0.9999 at batch 8 only) plus the 0.99/0.995 bars elsewhere. A partial corruption (e.g. of the child's `l` in `dst_reg_4`) would sit inside the batch-1 bars.
How to verify: on the device, run the per-head branch at batch 1 / S 8192 with `dst_full_sync_en=true` and compare bitwise with the default; a difference beyond bf16 rounding of the merge confirms the window matters in the per-head branch too. Cheaper: temporarily swap the per-head merge to the primitive sequence and compare.
Suggested fix: use the primitive merge (or a two-acquisition `correction_block`) in both branches so the shipped kernel does not depend on an unexplained timing property; report the batch-1 fidelity of the stock op alongside, since it shares the helper.

### [Important] The shipped G-LRD path (group-shared + in-kernel V + `dst` + table multicast) has no op-level check that the multicast is bit-identical; the bit-identity claim is established only for per-head absorbed-V layouts
File: `tests/test_palu_sdpa_device.py:525-556` (`test_table_mcast_is_bit_identical`: per-head, `r_k=32, r_v=128`, no `u_v`, batches 32/8/1/5, S <= 2048); `:244-260` (`_fused_group` defaults `table_mcast=False`; no group test passes `True`); `tests/test_attention_device.py:335-370` (both models built with `PaluRuntime.table_mcast=True`, so it compares group vs per-head with the multicast on both sides, PCC 0.99); `docs/results/stage2e.md` ("multicast is bit-identical to the per-core read on all five layouts").
What: The `glrd_50_fk2gdm`/`glrd_70_f256_l4_fk2gdm` rows and the stage 2e "H=2 group mode" fidelity numbers run `PALU_GROUP_SHARED` + `PALU_RECON_V` + `PALU_TABLE_MCAST`. In group mode the leader also owns H resident weight blocks and the receivers' reader continues into `read_w_rot` x H after the semaphore wait; none of that combination is exercised with the multicast at the op level, nor is any multicast case at r_k >= 64, with in-kernel V, at S >= 4096, or at batch 16.
Why it matters: coverage gap on a used path. The mechanism is orthogonal (the table only reaches `c_13`/`c_14` differently) so a defect is unlikely, but the external claim of bit-identity is broader than its evidence.
How to verify: add `table_mcast` to the parametrisation of `test_group_shared_batch32_matches_stock_split` and `test_group_shared_with_sequence_split_matches_per_head`, and a mcast-vs-no-mcast `torch.equal` case through `_fused_group` at batch 8 / S 4096.
Suggested fix: as above; state the layouts the bit-identity claim covers in stage2e.md.

### [Important] The fused path has no guard against the known chunk-32 defect and no test at chunk 32/64
File: `palu_tt/attention.py:298-300` (`chunk = ... or fused.chunk_size(self.max_seq_len)`), `palu_tt/fused.py:53-58`, `K/palu_sdpa_decode.cpp:66-77` (accepts any power of two >= 32), `device_operation.cpp:556` (Phase 2 forces fp32 accumulate), `palu_tt/attention.py:518-531` (`_recon_len` documents the defect and rounds the *naive* path to 64).
What: The stock decode op mis-reduces at K chunk 32 with fp32 accumulate when a user's chunks span several cores (batch < 32; memory note and `_recon_len` docstring: PCC 0.17 at S=160). The Palu kernel inherits the whole reduction path and additionally mandates fp32 accumulate in Phase 2. For any `max_seq_len` whose largest power-of-two factor is 32 the fused chunk defaults to 32 at batch < 32 with nothing to stop it, and the suite never runs chunk 32 or 64 (only 128, 256 via the S=256 envelope tests, and 512).
Why it matters: no reported number is affected (all result contexts are powers of two >= 1024 or multiples of 1024, decode_check uses 2048), but it is a silent-wrong-answer path one flag away, and the fused op's susceptibility is inferred from shared code, not measured.
How to verify: op test at S=160 or S=2080, batch 8, Phase 2, chunk left to the default.
Suggested fix: `TT_FATAL(k_chunk_size >= 64 || B == 32)` (or refuse chunk 32 under fp32 accumulate) in the wrapper, and have `attention.py` round the default chunk up to >= 64 as `_recon_len` does; add the test either way.

### [Important] The Phase-2 drift claim ("16 steps at 8k drift by well under a bf16 ulp") is not bounded by any test, and the one 16-step test cannot see it
File: spec 2026-09-10 §5 and `palu_compute_common.hpp:188-195` (claim); `tests/test_palu_sdpa_device.py:203-205` (batch 32, S 8192: the only case where one core steps the state 16 times), `:198-201` (batch 1: <= 15 seeding steps then one chunk).
What: The batch-32 8k test is one of the insensitive cases above (a kernel with no stepping at all scores 0.9917 against its 0.99 bar), so the drift after 16 in-loop steps is bounded only by the batch-1 seeding tests, whose per-row bar (0.99 on one full-context row) corresponds to ~10 % RMS error. A simple model of the step (fp32 state, products rounded to 11 mantissa bits, `scratchpad` inline check) gives a worst-case relative drift of 4.8e-3 after 16 steps of R_{-512} -- about one bf16 ulp, not "well under"; with a bf16 state it would be 3.6e-2, so keeping the state in fp32 does what it is meant to. The measured PCC values that the stage 2 report says were checked (Task 4) are not recorded anywhere in the repo.
Why it matters: unverified claim in the design docs; low numerical impact (a 1-ulp rotation error on the query is invisible at PCC 0.999), but the claim should match the evidence.
How to verify: op test at batch 32 (or all rows at `S-1`) with S = 8192, per-row PCC >= 0.999 against the fp32 reference, in all three rot modes.
Suggested fix: add that test; reword the claim to "about one bf16 ulp worst case, measured PCC ...".

### [Minor] The RoPE-convention tests are circular; the convention is nevertheless correct (verified against the device op's kernel)
File: `tests/test_fused.py:8-16, 92-103` and `tests/test_palu_sdpa_device.py:58-67, 91-103, 262-278`: reference and "stock" comparisons all build T/cos/sin with the same `fused.rope_transformation_matrix` / `fused.cos_sin_tables` that build the op's inputs, so a wrong convention would pass everywhere except the model-level tests.
What I verified: `rotary_embedding_llama.cpp:94-145` computes `rotated = x @ trans_mat; out = x*cos + rotated*sin` with `trans_mat = get_rot_transformation_mat(32)` (`tensor_utils.py:74-95`: +1 at (2i,2i+1), -1 at (2i+1,2i)) -- identical to `fused.reference_decode` and to `w_rot = [u_k | u_k T]`; the model's decode `rot_mats` (`RotarySetup`, `rope.py:793-808`) and `fused.cos_sin_tables` call the same `compute_gather_cos_sin(theta, rope_scaling)`, so the llama3 scaling (`LlamaRotaryEmbedding.apply_scaling`) and theta are shared; the tables are Meta-interleaved (`gather_cos_sin` stacks each frequency twice). The Phase-2 identities were checked numerically (T^2 = -I; (x*cos)T = (xT)*cos; `palu_step_q` = R_{-c} with the second half equal to q~'T; q R_p . k R_{s0+t} = (q R_{p-s0}) . (k R_t) after 15 R_{-c} steps, with non-uniform per-pair frequencies), and the kernel's index arithmetic (cos at `i*Wt+j`, sin at `+DHt`; A columns `w_base+j`, B columns `w_base+j+DHt`; K_rot at `j*Sk+i`, the layout `matmul_blocks(transpose=true)` reads; seeding `k_chunk_start` steps; step before each later chunk) matches.
Suggested fix: one op-level test that rotates Q with `ttnn.experimental.rotary_embedding_llama` (decode mode) and K on the host with the same tables, at a position >= 4096.

### [Minor] The runtime H fallback fired in two result runs; the JSON shows the post-fallback H but nothing marks it as a fallback, and the warning does not name the layer
File: `palu_tt/attention.py:640-656` (catch `RuntimeError` containing "ircular buffer", halve H, `record_group_heads`); `palu_tt/bench.py:141, 220, 296, 461-465`; `docs/results/raw/decode_check_glrd_70_fk2g.log:1082`, `bench_decode_glrd_70_fk2g2.log:468,933,1398` ("heads_per_core=2 does not fit L1 ... falling back to 1").
What: Both runs forced `--group-heads 2` and the 512/512 layer 31 fell back to H=1 at every context; the JSONs record `group_heads: "2"` with `group_heads_per_layer = [2]*31 + [1]`, which is what ran (verified: recording happens inside the except branch and `GROUP_HEADS` is copied after the timed steps). The `auto` rows show no fallback in any log. ## Verdict

The kernel's arithmetic and index plumbing are correct as far as reading can establish: the rotation packing, the chunk-relative Phase-2 recurrence (signs, seeding, per-chunk step), the group-mode ring/peel bookkeeping, the multicast roles and the host L1 model all match the code and the stock RoPE convention, and the stock op is untouched so baseline rows are unaffected. The weak point is the evidence, not the kernel: the batch >= 8 op-level reference checks are near-inert (a kernel with no Phase-2 stepping passes them), the per-head merge keeps a helper known to overflow the fp32 DST window on an unexplained "it happens to work" basis, and the shipped G-LRD combination (group + in-kernel V + dst + multicast) and the production fidelity/layout are validated only by loose model-level PCCs. No reported number was found to be wrong or misdescribed; the H fallback that did fire is recorded correctly, if opaquely.

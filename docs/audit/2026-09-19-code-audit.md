# Code audit of the Palu-on-n300 study (2026-09-19)

Everything in this repository was written by an AI coding agent between 2026-09-09 and 2026-09-18 (140 commits). Before the results are presented outside the group, all of that code was audited: the measurement harnesses, the model port, the fused kernel, the calibration pipeline, the reporting code and the tests. This document is the consolidated result. The seven per-area reports, with every finding's file:line, verification command and suggested fix, are in `docs/audit/reports/`.

## 0. Summary

**The measurements are sound. The document that summarises them is not yet.**

- Every auditor independently re-derived the numeric path of its area and found the arithmetic correct: the perplexity windows and scoring, the log-likelihood adapter (position for position against lm-eval's own scorer), the latent/K-rebuild/RoPE/V-fold mathematics under GQA on two chips, the fused kernel's rotation packing and Phase 2 recurrence (checked against tt-metal's own RoPE kernel and numerically), the calibration recipe (Palu's `fisher_uniform` + `whiten`, run through upstream's own `compress.py`), and the report generator (all six stage documents regenerate byte-identically from the raw JSONs; roughly 160 numbers in the hand-written prose checked, only rounding-level slips).
- **Seven findings are rated Critical. All seven are sentences in `docs/report_palu_on_tt.md` (the external report) that the repo's own raw files or code contradict**, in every case where the stage documents state the fact correctly. Fixing them changes wording and one figure, not a measurement.
- **Thirty-eight Important findings** fall into four groups: (1) protocol differences that were never disclosed and that affect comparison with the paper and with the GPU cross-check (BOS token in task scoring; blind-versus-faithful prefill rows differenced in one column; GPU and n300 dumps sharing ranks but not factors); (2) reproducibility holes (headline rows measured under a CLI default that has since changed and whose documented reproduction command would overwrite them; per-layer ranks and provenance ids not in the repo); (3) three infrastructure defects that could make a *future* number wrong silently (the device-idle gate's own-process check is unreachable under `pipefail`; the JIT-cache purge hashes five of eleven kernel source files; the profiler's per-step divisor is hand-typed); (4) tests that cannot fail on the thing their docstring says they guard.
- **What needs to happen before the report is presented** is in section 6: about fifteen wording corrections, one figure, one file rename plus regeneration, and three optional device re-measurements (about 1.5 hours of board time) that would remove the two remaining caveats from the headline table.

## 1. Scope and method

**What was audited.** All 59 code files the agent wrote: `palu_tt/` (23 files, 5,414 lines), `scripts/` (14 files, 2,166 lines), `tests/` (22 files, 4,259 lines), the fused op in the tt-metal submodule branch `palu-sdpa` (17 files, 5,042 lines of C++ and kernel code), the runtime patch set applied to `third_party/palu`, and the two document generators. Each area's auditor also read the documents that make claims about its code (`README.md`, `docs/report_palu_on_tt.md`, `docs/results/stage*.md`, the specs) and the raw result files those claims rest on.

**How.** Seven independent reviewer sessions, one per area, each given the file list, the documented claims to trace, and the shared-server rules (read-only on the repository, no device access, CPU-only checks under `nice`, no calibration or patch scripts). Each returned a report in a fixed format: scope actually read, findings by severity with file:line and a verification a human can repeat, a per-test-file verdict on whether the test could pass with the bug present, a table tracing every documented claim to the code that implements it, and a verdict. Severity means: **Critical** = a reported number is wrong or the code does not measure what the documents say; **Important** = could be wrong, an unverified claim, a test gap that leaves a numeric path unguarded, or a reproducibility hole; **Minor** = everything else. The coordinating session then verified every Critical and Important finding independently against the files before including it here, and ran the empirical checks in section 5.

**What was executed.** CPU-only: the report tests (50), the adapter tests (7), the patch tests except the one that mutates the submodule; regeneration of all six stage documents to a scratch directory; standalone torch replications of the model-path mathematics (with mutation controls) and of the kernel test's PCC sensitivity; a CPU comparison of the task adapter against lm-eval's scorer on the fp32 model. On the device: one perplexity run (section 5.4), launched through the gate after all auditors had finished.

## 2. What was verified correct

These are positive findings, stated so that a reader knows what the audit establishes and not only what it faults. Each was traced to code and, where marked, reproduced.

**Perplexity.** wikitext-2-raw-v1 test split joined with `"\n\n"`, tokenised once (289,077 tokens, one BOS at index 0, reproduced), 141 non-overlapping 2048-token windows, 2047 scored positions each (288,627, matches every raw file exactly), `--windows k` takes the first k. Pre-final-norm hidden states from the device; the real final norm (eps 1e-5), the real untied LM head and the cross-entropy in fp32 on the host; token-weighted aggregation; logits/targets aligned (512-chunked head equals a one-shot cross-entropy to 4.6e-8). Palu's own `run_ppl_eval.py` is arithmetically the same protocol (its mean of per-window means equals our token-weighted sum because every window scores 2047 tokens), so the GPU-versus-n300 perplexity comparison is like for like. All 78 raw perplexity files satisfy `exp(nll/tokens) == ppl` and `tokens == windows*(seq_len-1)`.

**Task scoring.** The adapter's log-likelihood is position-for-position identical to lm-eval 0.4.2's HFLM (rows L-1-n..L-2 predict the last n tokens), no padded position is scored, requests and results stay aligned, memo keys include the continuation length, `limit` is null on every reported row. The three `_hub` task configs differ from the stock ones only in dataset id (confirmed from the `configs` block recorded in every raw file). Splits and document counts are the standard ones (500 / 1838 / 2376 / 1172 / 1267; 22,398 requests). `acc`, not `acc_norm`, is what the tables average, and all fourteen raw task files recompute to the tabled means.

**Model path.** Latent `h = x @ VT^T`; K rebuilt as `latent @ U_k` with the Meta head permutation folded into `U_k` so the stock prefill-mode RoPE applies over positions 0..S-1; the V up-projection folded into `wo` with KV head g applied to the four query heads that read it, consistent with the TP-2 head sharding; the attention scale unchanged; G-LRD's shared latent with per-head U slices, V not absorbed, one group per chip asserted. All re-derived in a from-scratch torch replication for six shapes and two group sizes, with a mutation control proving the check is not vacuous. The weight-cache tag was checked for completeness: no input that changes a cached tensor's content is missing from it. `_recon_len` keeps the naive decode path off the known chunk-32 defect.

**Benchmarks.** The decode timing region is H2D copy + forward + `ttnn.synchronize_device`; batch 32 with all users at the claimed position and a K rebuild over the full cached length; `decode_check` feeds both builds the same wikitext tokens (teacher forcing from the dataset, not from either model) and compares full-vocabulary fp32 logits over 63 steps; the profile aggregator windows on the signposts and divides by the step count; every recorded field in all 132 bench files agrees with its file name.

**Reporting.** All six stage documents (1, 2, 2b, 2c, 2e, 2f) regenerate byte-identically from the committed raw JSONs. Bytes per token (`1.0625 B per bfp8 element x half the layer's latents per chip`), the compression ratio, the five-task and paper-protocol averages, slopes, the frontier's Pareto front and the `_fk2gdm` row mapping all reproduce independently. Of 39 spot-checked numbers in the report's prose, 33 match; the six that do not are listed below.

**Calibration.** The recipe is Palu's `fisher_uniform` + `whiten` through upstream's `compress.py` at the pinned commit. Every one of the 27 dumps has VT row counts equal to the sum of its ranks in all 64 modules, no nested directories, and no sign of the fp32-whitening damage in layers 0 and 1. The three `_f2048` dumps carry exactly the GPU's rank lists; the `--ranks_json` path skips only the rank search and reuses the same whitening cache and decomposition code. The Fisher cache reuse across ratios and group sizes is valid (Fisher is per-weight `grad^2`, independent of both). The 2048-versus-32/256-sample rank differences (1, 5, 7 and 4 of 64 modules, each one 32-step) were recomputed exactly.

**Kernel.** The stock `sdpa_decode` and `sdpa` directories are byte-identical to v0.78.0, so baseline rows are untouched by the kernel work. `w_rot = [u_k | u_k T]` with the pair-swap `T`, the Meta-interleaved tables, theta and llama3 scaling all match the device `rotary_embedding_llama` kernel and the model's own query rotation; the Phase 2 identities and the sign of the per-chunk query step were checked numerically; group-mode ring bookkeeping, multicast roles, the L1 model against the factory's CB allocation, and the runtime H fallback were traced and match the documents.

## 5. Empirical checks run by the audit

5.1 **CPU fp32 versus device, same windows.** `ppl_cpu_baseline.json` (7.357, 20 windows) against `ppl_baseline_20w.json` (7.400, the device on the same 20 windows): the device is +0.042 above fp32 CPU. Against Palu's fp16 GPU script on 141 windows (7.213 vs 7.254) it is +0.041. Two independent estimates of the port's arithmetic cost on the baseline agree to 0.001. The apparent "7.36 vs 7.25" in the raw directory is the window count (20 vs 141 moves the baseline by 2.0 %), not a CPU-versus-device gap.

5.2 **Regeneration.** All six stage documents regenerated from `docs/results/raw/` are byte-identical to the committed files apart from the header line.

5.3 **Task adapter versus lm-eval's scorer (CPU, fp32 model, 100 documents per task).** `palu_tt.lm_eval_tt.TTLM` driven by an HF fp32 forward, against lm-eval 0.4.2's `HFLM` on the same model object with `add_bos_token=True` and with the default `False` (Palu's `run_lm_eval.py` setting), on OpenBookQA, ARC-challenge and WinoGrande, comparing per-choice log-likelihoods and accuracy. Script: `docs/audit/reports/scripts/adapter_equiv.py`; per-choice outputs in `docs/audit/reports/adapter_equiv_results.json`. **Result.** Against `HFLM(add_bos_token=True)` the adapter's per-choice log-likelihoods agree to at most 3e-5 nats over the 1,000 choices (mean 3e-6, fp32 noise) and every accuracy is identical (OpenBookQA 0.34 / acc_norm 0.43, ARC-challenge 0.55 / 0.52, WinoGrande 0.71): **the adapter is exactly lm-eval's scorer with a BOS token.** Against `HFLM(add_bos_token=False)`, Palu's setting, the per-choice log-likelihoods differ by up to 4.4 to 5.7 nats and the 100-document accuracies move by a few points in either direction (OpenBookQA 0.34 to 0.34, ARC-challenge 0.55 to 0.51, WinoGrande 0.71 to 0.74). So the BOS choice moves individual task scores by an amount of the same size as the n300-versus-GPU differences (up to 2.6 points on 500 to 2,400 documents), and not uniformly in one direction; a 100-document sample cannot resolve the per-task sign. The within-study comparisons are unaffected because every row was scored the same way. Recommendation stands: disclose the BOS setting, and re-score the stock row without BOS on the device (52 min) if a like-for-like number against the paper or the GPU run is wanted.

5.4 **Identity row re-measured.** `eval_ppl --row identity_recheck --kind palu --no-latent-quant-in-prefill` on the current code, 141 windows, 2026-09-19 14:45 (`docs/results/raw/ppl_identity_recheck.json`). **Result: nll 571,928.3628845215, bit for bit equal to `ppl_baseline.json`.** So the current identity path is exactly stock in prefill, as README and stage1.md claim, and the committed `ppl_identity.json` (7.2552) is a stale measurement of the code before the Task 12 fast paths. C7 resolves as: replace the identity row with the re-measurement and change the report's "reproduces the baseline to three decimals (7.255 vs 7.254)" to "is bit-identical to the baseline (same 571,928.36 nats over 288,627 tokens)"; add the `torch.equal` assertion (I43) so it stays that way.

5.5 **Model-path mathematics** (`docs/audit/reports/scripts/math_check.py`, `math_check_mut.py`): a from-scratch torch replication of the latent, the K rebuild with the Meta permutation, prefill RoPE, the `U_v` fold under GQA and the G-LRD indexing, for six shapes; all agree with the converter's tensors to fp32 noise, and the mutated version fails as it should.

5.6 **Kernel test sensitivity** (`docs/audit/reports/scripts/pcc_sensitivity2.py`): a pure-torch model of the op test's inputs shows a kernel without Phase 2 query stepping scoring 0.9977 and 0.9917 against the 0.99 bar at the batch-32 shapes, and 0.45 to 0.79 at batch 1.

5.7 **Dumps.** All 27 `compressed/` dumps: VT row counts equal the rank sums in every module; no nested output directories; layer-0/1 factor magnitudes in family with the other layers; the `_f2048` dumps' ranks equal the committed GPU rank files byte for byte.

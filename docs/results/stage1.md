## Setup

- Model: `meta-llama/Llama-3.1-8B-Instruct` (32 layers, 32 query heads, 8 KV heads, head_dim 128,
  hidden 4096). On one n300 with TP=2 that is 16 query heads and 4 KV heads per chip.
- Device path: tt-metal v0.78.0 `tt_transformers`, bfp8 weights and bfp8 KV/latent caches,
  non-paged caches, untraced decode, `use_qk_fused=False` for both the stock and the Palu model.
- Rows. `baseline` is stock `tt_transformers` attention. `identity` is `PaluAttention` with
  `r_k = r_v = 128`, i.e. the same code path as the compressed rows but with a full-rank (lossless)
  factorisation — it isolates the cost of the plumbing. `svd_r96`, `svd_r64` and `svd_rk128_rv64`
  are plain per-head truncated SVD of `k_proj`/`v_proj` (group size 1, no calibration), exported by
  `palu_tt/compress.py` to `compressed/<row>/`; ranks come from each folder's
  `config.json:palu_tt.rank_k/rank_v`.
- Perplexity: wikitext-2-raw-v1 test split (`Salesforce/wikitext`), joined with `"\n\n"` and
  tokenized once, then 141 non-overlapping 2048-token windows = 288,627 scored tokens
  (`docs/results/raw/ppl_<row>.json`: `windows`, `tokens`). The device forward returns
  pre-final-norm hidden states; the final RMSNorm, `lm_head` and cross-entropy are done on the host
  in fp32. Only window 0 carries a BOS token — identical for every row, so it cannot bias the
  stock-vs-Palu comparison, but it does mean these absolute numbers are not comparable to published
  sliding-window base-model perplexities.
- CPU column: the same windows through an fp32 HF model on the host, 20 windows only
  (`ppl_cpu_baseline.json`); it is a harness cross-check, not a headline number.
- KV bytes: measured from the allocated caches. Stock stores K and V at head_dim 128; Palu stores
  latents of `r_k + r_v` per KV head. The second KV column is the first one multiplied by 32 layers
  and 2 chips, i.e. bytes per token for the whole model on the board: 68.0 KiB stock, 51.0 KiB at
  `r96` and `rk128_rv64`, 34.0 KiB at `r64`.
- Max context: the largest power-of-two `max_seq_len` that allocates at batch 32
  (`bench_maxctx_<row>.json`, with the failing size and its allocator error).
- Timing: batch 32, `max_seq_len == context`, warm-up iterations then the median and minimum of the
  timed ones (decode 3+10, attention-only 3+20, prefill 2+5 at batch 1). Device sync is inside the
  timed region.
- Samples: greedy, 48 new tokens, batch 1, `max_seq_len` 2048.
- All rows were run sequentially through `scripts/run_device.sh` (which refuses to start on a busy
  board) between 2026-09-09 23:20 and 2026-09-10 01:14; the run log is
  `docs/results/raw/matrix.log`. The raw JSONs are gitignored; re-render this file with
  `python -m palu_tt.report`.

## Headline findings

**a. The Palu path costs nothing in perplexity when the factorisation is lossless.** `identity`
(same `PaluAttention` code, latent caches, per-step K reconstruction, MLA decode op and fused
`wo_fused` output projection, but at full rank 128) scores 7.255 against stock 7.254 over the same
141 windows — a difference of +0.001, i.e. 0.02 %. Whatever the compressed rows lose is lost in the
factorisation, not in the port. This matches the Task 7 device parity test (identity-vs-stock
prefill logit PCC 0.9994, 32/32 identical teacher-forced tokens).

**b. Uncalibrated per-head SVD destroys quality, even at rank 96.** 79.4 at `r96` (10.9x the stock
perplexity) and 703.6 at `r64` (97x). The generation samples show the failure mode directly: both
compressed rows fall into immediate repetition loops ("the first time the first time …",
"Write a haiku about matrices." repeated verbatim) while the stock row produces ordinary text. This
is *not* the accuracy result for Palu — it is the result for plain truncated SVD with no
calibration, which is Palu's own ablation floor. The meaningful comparison is the calibrated recipe
(Fisher-based uniform rank search + whitening), which is running now and will land as the
`palu_full_50` row; for reference, the Palu paper (arXiv 2407.21118) reports wikitext2 8.28 →
10.11 for Llama-3-8B-Instruct at 50 % KV compression with its full G-LRD recipe. No conclusion
about Palu's accuracy should be drawn from this table until that row exists.

Two things in the quality column are worth carrying into the calibrated run:

- At an equal cache budget (816 B/token/layer/chip), splitting the budget evenly (`r96`: 79.4) is
  6.3x better than spending it all on K (`rk128_rv64`, K exact at rank 128, V truncated to 64:
  502.7). Rank allocation dominates — which is exactly what Fisher-based rank
  search is for.
- Truncating V alone to rank 64 already costs 502.7 of the 703.6 seen when both are truncated to
  64, so at this rank most of the damage comes from V, not from K.

**c. The compressed rows shrink the cache and double the batch-32 context limit.** KV bytes per
token per layer per chip go 1088 → 816 (`r96` and `rk128_rv64`, 1.33x) → 544 (`r64`, 2.00x); for
the whole model on the board that is 68.0 → 51.0 → 34.0 KiB per token. The largest batch-32 context
that allocates goes from 4096 (stock and `identity`, 8192 fails with a 136 MiB DRAM allocation
error) to 8192 for all three compressed rows (16384 fails). This is the one headline benefit that
is already real at stage 1, and it is unaffected by the host contention.

**d. Per-step K reconstruction dominates the Palu decode step, and it is rank-independent.**
Attention-only, comparing minima (the stable statistic here), the Palu rows cost about 3x stock at
1k (stock 1.14 ms; identity 3.27, `r96` 3.71, `r64` 3.55, `rk128_rv64` 3.45), about 5x at 4k (stock
1.76 ms; 9.00 / 9.58 / 9.06 / 9.31) and about 6x at 8k (stock 2.66 ms; 16.42 / 16.81 / 15.68 /
16.08). Two observations follow:

- Multiplied by 32 layers, the attention block accounts for essentially the whole Palu decode step
  (e.g. `r64` at 8k: 32 x 15.68 = 502 ms against a 486 ms whole-step minimum; the small excess is
  the per-layer microbenchmark's own fixed overhead), whereas for stock at 1k it is 37 ms of a
  48 ms step. Decode for the Palu rows is the reconstruction.
- The four Palu rows land on top of each other despite ranks of 128/128, 96/96, 64/64 and 128/64:
  the spread of the attention-only minima across them is 13 % at 1k and under 8 % at 4k and 8k.
  The cost therefore tracks the reconstruction *output* — a
  `[32, 4, S, 128]` scratch write plus a RoPE rotation over the whole window every step — and not
  the rank of the latent matmul. In particular `identity`, which reconstructs at the largest rank,
  is not the slowest row. This is precisely the cost that stage 2's fused kernel removes.

  A consequence to record: the spec's section 9 expectation that "decode latency with V-only
  compression is no worse than baseline" is **not** met by `svd_rk128_rv64` (whole-step minimum
  105.5 / 278.3 / 500.1 ms at 1k/4k/8k, i.e. indistinguishable from the other Palu rows and far
  above stock). V-only compression avoids *truncating* K, but in this implementation K is still
  stored as a rank-128 latent and reconstructed every step, so it pays the full reconstruction
  cost. A row that keeps K in the stock cache and compresses only V would be a different
  implementation, not a different rank setting.

Prefill is unaffected: TTFT p50 spans 441.3–448.6 ms at 2048 tokens (1.7 % spread across all five
rows) and 2107.6–2119.5 ms at 8192 tokens (0.6 %), with no ordering that separates stock from Palu.
Prefill reconstructs K and V in full and then runs ordinary attention, so this is expected.

## Preliminary timings — read this before quoting any millisecond

Every decode, attention and prefill cell above was measured while a 12-thread CPU calibration job
was running on the same host. Untraced decode is host-dispatch-bound, so the medians carry host
jitter: stock decode at 1k is 81.6 ms p50 against a 48.5 ms minimum, and the stock p50 at 4k
(70.0 ms) is *lower* than at 1k, which is impossible for real device work and is pure host noise.
Ratios computed from p50 are correspondingly unreliable (stock attention p50 at 8k, 2.9 ms, is
below its own 4k value of 4.2 ms). The comparisons in finding (d) therefore use `min_ms`, and only
the order-of-magnitude conclusion (reconstruction dominates; it grows with context; it is
rank-independent) is claimed. **All timing rows will be re-measured on an idle host before this
document is final**; the quality, KV-memory and max-context columns are unaffected by the
contention and are final.

## Notes from the port (verified in earlier tasks)

- **No fallback was needed for the MLA decode op.** `flash_multi_latent_attention_decode` accepted
  the GQA configuration (16 query heads / 4 KV heads per chip) with a separate V tensor of head
  dim `r_v`, so V is consumed directly from the latent cache and never reconstructed at decode.
  The spec's fallback (reconstruct V per step and use stock
  `scaled_dot_product_attention_decode`) is not in use.
- **The spec's "latent caches in bf16" fallback does not help and has been struck.** Prefill never
  reads the latent cache (it reconstructs in flight), so bf16 latents cannot change the prefill
  PCC, and switching them changed teacher-forced agreement by one token. The r64 fidelity gap
  (prefill logit PCC 0.963 against the fp32 CPU low-rank reference, versus 0.999 for stock against
  its own fp32 reference) comes from the reconstruction path — the bf16/HiFi2 `latent @ U_k`
  matmul plus bfp8 requantisation. The lever is matmul fidelity (HiFi4 / fp32 accumulate), not
  cache dtype.
- **Device-vs-CPU agreement.** On the 20-window subset the stock device model scores 7.400 against
  7.357 for the fp32 CPU model (0.57 %, Task 8 report), consistent with bfp8 device weights. The
  full 141-window device number in the table is 7.254. The r64 device model matches its own fp32
  CPU low-rank reference at teacher-forced token agreement 0.906, against 0.969 for the stock
  control — i.e. the compressed model is reproduced on device about as faithfully as the stock
  model is.
- **Bug found and fixed while benchmarking**: when the reconstruction window equals the cache
  length, `ttnn.slice` returns the input tensor itself, and the decode path was deallocating the
  module's persistent RoPE tables through that alias; every later decode step then failed. Fixed
  with a regression test (Task 9).
- **Operational**: polling `tt-smi` wakes the board, after which the device-idle gate reports busy
  for minutes — device runs must be launched directly and retried with a long backoff, never
  pre-polled.
- **Calibration plumbing**: Palu upstream hard-codes 2048 Fisher calibration samples (patched to
  honour `--n_fisher_calib_samples`), and transformers 5.x needed `position_embeddings` plumbing
  for Palu's whitening loop.

## Deviations from the stage 1 spec

Recorded in `docs/superpowers/specs/2026-09-09-palu-tt-stage1-design.md`: contexts are 1k/4k/8k
plus the max-context probe (not 16k, which does not allocate at batch 32); `wo_fused` is
zero-padded to 4096 x 4096; compressed weights are a delta file (`palu_attn.safetensors` +
`config.json`) rather than a full HF dump; the latent-dtype fallback is replaced by the
reconstruction-fidelity finding above; `set_recon_len` rounds to 256 rather than 32; and the
model-level acceptance bars actually used are logit PCC >= 0.95 against the fp32 CPU low-rank
reference and teacher-forced token agreement >= 0.85. The one deviation *not* yet reflected in the
spec is section 9's V-only latency expectation, discussed in finding (d).

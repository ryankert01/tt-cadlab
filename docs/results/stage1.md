## 1. Setup and provenance

- **Model**: `meta-llama/Llama-3.1-8B-Instruct` (32 layers, 32 query heads, 8 KV heads, head_dim 128,
  hidden 4096), read from the user's read-only HF cache. On one n300 with TP=2 that is 16 query
  heads and 4 KV heads per chip.
- **Hardware / stack**: one Wormhole n300 (two chips, TP=2), Intel i7-14700 host, Ubuntu 22.04.
  tt-metal **v0.78.0** built from source with clang-20; `tt_transformers` from that tag; torch CPU,
  `transformers` 5.12.1. bfp8 weights and bfp8 KV/latent caches, **non-paged** caches, **untraced**
  decode, and `use_qk_fused=False` for *both* the stock and the Palu model so the two are compared
  through the same attention plumbing.
- **Rows.** `baseline` is stock `tt_transformers` attention. `identity` is `PaluAttention` with
  `r_k = r_v = 128` — the same class, converter and cache plumbing, but a lossless factorisation;
  since Task 12/14 it takes the full-rank fast paths on both K and V, so it is bit-identical to
  stock in the attention block and measures the cost of the *plumbing* only. `svd_r96`, `svd_r64`
  and `svd_rk128_rv64` are plain per-head truncated SVD of `k_proj`/`v_proj` (group size 1, **no**
  calibration) from `palu_tt/compress.py`. `palu_full_50` and `palu_full_70` are Palu's own recipe —
  Fisher-information uniform rank search plus whitened decomposition, group size 1 — run on CPU in
  fp32 from `third_party/palu`, at target ratios 0.5 and 0.7 (`compressed/palu_full_0.5`,
  `compressed/palu_full_0.7`).
- **Ranks.** The plain-SVD rows are uniform, so `r_k`/`r_v` come from each dump's
  `config.json:palu_tt`. The calibrated dumps have no `palu_tt` block; their per-layer ranks are
  read from `head_wise_ranks` through `palu_tt.convert.load_palu_dir` — the same reader the device
  uses — and reported as a range with the mean. Ratio 0.5: `r_k` 32 in 31 layers and 64 in the last;
  `r_v` 128 in layers 0–17, 64 in 18–29, 96 in 30–31. Ratio 0.7: `r_k` 64 in 23 layers, 32 in 8, 128
  in the last; `r_v` 128 in 25 layers and 96 in 7.
- **Perplexity**: wikitext-2-raw-v1 test split (`Salesforce/wikitext`), joined with `"\n\n"` and
  tokenized once, then 141 non-overlapping 2048-token windows = 288,627 scored tokens. The device
  forward returns pre-final-norm hidden states; the final RMSNorm, `lm_head` and cross-entropy run
  on the host in fp32. Only window 0 carries a BOS token — identical for every row, so it cannot
  bias the stock-vs-Palu comparison, but these absolute numbers are not comparable to published
  sliding-window base-model perplexities.
- **CPU column**: the same windows through an fp32 HF model on the host, 20 windows only. It is a
  harness cross-check, not a headline number; the window-count difference alone moves the stock row
  by 2.0 % (device 7.400 on those 20 windows vs 7.254 on all 141).
- **Timing**: batch 32, `max_seq_len == context`, warm-up then median and minimum of the timed
  iterations (decode 3+10, attention-only 3+20, prefill 2+5 at batch 1). Device sync is inside the
  timed region. The attention-only bench builds **layer 0 only** (`args.n_layers = 1`).
- **The device-idle gate.** Every device run goes through `scripts/device_free.sh`, which refuses to
  start when telemetry shows the n300 busy or when another of our jobs holds it. The board is shared
  with other users on this host and their processes are not visible to us.
- **Provenance of the timings.** The first matrix run (2026-09-09 23:20 → 2026-09-10 01:14) was
  taken while a 12-thread CPU calibration job was resident; untraced decode is host-dispatch-bound,
  so those medians were inflated and non-monotonic in context. **They were discarded.** Every
  decode/attention/prefill cell above was re-measured on an idle host on 2026-09-10 between 07:51
  and 09:06, with all Palu rows on the post-Task-12 code (V-only fast path) — check the mtimes of
  `docs/results/raw/bench_*.json`. Perplexity, KV-memory and max-context columns were never affected
  by the contention.
- **Not recorded**: the tt-smi firmware/driver versions and the other users on the board. Polling
  `tt-smi` wakes the n300 out of idle, after which the idle gate reports the board busy for minutes
  and blocks the next run, so it was deliberately never queried during the measurement window.
- The raw JSONs (`docs/results/raw/*.json`) are gitignored. Re-render this file with
  `python -m palu_tt.report`; everything below the marker is hand-written and preserved.

## 2. Findings

### (a) The port is faithful: the Palu path adds no error, and the device agrees with fp32 CPU

`identity` — same `PaluAttention` class, same converter, same latent caches and fused output
projection, at full rank — scores **7.255** against stock **7.254** over the same 141 windows
(+0.0013, 0.018 %). Decode is **38.3 / 38.2 ms** p50/min at 1k against stock **38.1 / 38.0**, and
TTFT is 443.1 vs 439.7 ms at 2048 tokens. The device tests behind this row are prefill logit PCC
**0.9994** identity-vs-stock and **32/32** identical greedy tokens (Task 7, re-confirmed in Tasks 12
and 14); after Task 12's full-rank shortcuts the identity attention block is bit-identical to stock
(max-abs difference 0.0 on caches and outputs). Whatever the compressed rows lose is lost in the
factorisation, not in the port.

The independent check is the fp32 CPU reference, run on the same windows:

| row | device | CPU fp32 (20 windows) | gap |
|---|---|---|---|
| `baseline` | 7.400 (20 windows) | 7.357 | 0.57 % |
| `palu_full_50` | 12.931 (141) | 12.759 | 1.3 % |
| `palu_full_70` | 9.028 (141) | 9.059 | 0.3 % |
| `svd_r64` | 703.6 (141) | 776.4 | same order; both degenerate |

The two calibrated rows agree with an fp32 CPU low-rank model that shares no code with the device
path, to within the spread the differing window count already produces on the stock row. That is the
strongest available statement that the converter and `PaluAttention` implement the same
factorisation the calibration produced.

### (b) Accuracy: calibration is the whole story

**Uncalibrated per-head SVD is catastrophic**, even at 75 % of head_dim: `svd_r96` **79.4** (10.9x
stock), `svd_r64` **703.6** (97x), and V-only truncation to rank 64 with K left exact
(`svd_rk128_rv64`) **502.7**. All three loop immediately in the samples. This is not Palu's accuracy
result — it is plain truncated SVD with no calibration, i.e. Palu's own ablation floor.

**Palu's full recipe recovers the model.** With Fisher-information uniform rank search and whitened
decomposition (group size 1, per-head / M-LRD):

| row | ppl | vs stock | KV bytes vs stock |
|---|---|---|---|
| `palu_full_70` | **9.028** | 1.24x | 69.9 % (1.43x reduction) |
| `palu_full_50` | **12.931** | 1.78x | 52.7 % (1.90x reduction) |

For comparison, the Palu paper (arXiv 2407.21118) reports for Llama-3-8B-Instruct at 50 % KV
compression **12.38 against its own 8.28 baseline** with the per-head (M-LRD) recipe — a 1.50x
ratio, against our 1.78x at 50 % — and **10.11** (1.22x) with medium-grained grouping (G-LRD, group
size 4), which we do not implement. Our 50 % row is therefore in the right region for M-LRD but
somewhat worse than the paper's; the absolute perplexities are not directly comparable (different
model revision, our 141 non-overlapping windows with a single BOS, bfp8 device weights).

Two CPU experiments run while chasing the calibrated row identify *where* the loss is, on a short
fixed text (stock 11.7 on that text):

| CPU experiment (short text) | ppl |
|---|---|
| stock | 11.7 |
| calibrated **V only**, K left stock | **13.0** |
| calibrated **K only** (rank 32), V stock | 25.9 |
| calibrated K + V | 28.2 |
| plain SVD, K only at rank 32 | 61.1 |
| plain SVD, K + V at the same ranks | 78.4 |

Two conclusions: **whitening works** — at identical rank it is 2.4x better than plain SVD on K
(25.9 vs 61.1) — and **K at rank 32 carries essentially all of the loss**; the calibrated V
factorisation, which the ratio-0.5 search leaves at full rank in 18 of 32 layers, costs almost
nothing. That is consistent with the two calibrated rows: ratio 0.7 spends its extra budget mostly
on K (mean `r_k` 58 vs 33) and recovers most of the perplexity.

### (c) Memory and capacity: the benefit that is already real

KV bytes per token, per layer, per chip (bfp8, 4 KV heads per chip, `4 · (r_k + r_v) · 1.0625`):

| row | B/token/layer/chip | B/token, whole model | KiB/token | max ctx @ batch 32 |
|---|---|---|---|---|
| `baseline`, `identity` | 1088 | 69,632 | 68.0 | 4096 |
| `svd_r96`, `svd_rk128_rv64` | 816 | 52,224 | 51.0 | 8192 |
| `svd_r64` | 544 | 34,816 | 34.0 | 8192 |
| `palu_full_50` | 574 (mean) | 36,720 | 35.9 | 8192 |
| `palu_full_70` | 761 (mean) | 48,688 | 47.5 | 8192 |

Every compressed row doubles the batch-32 context ceiling, from 4096 to 8192. Note that `bench`
reports the layer-0 figure, which for the two calibrated rows (r_k 32, r_v 128 in layer 0 for both)
is 680 B and is *not* the model: the table shows the mean over the 32 layers, rescaled from the
measured layer-0 value by the mean rank sum from `head_wise_ranks`.

16384 does not allocate for any row, but for two different reasons, visible in the failing
allocation size recorded in `bench_maxctx_*.json`:

- `svd_r96`, `svd_rk128_rv64` and `palu_full_70` fail on a **KV cache tensor** — 213,909,504 B is
  exactly `32 · 4 · 16384 · 96 · 1.0625`, and 142,606,336 B is the same for rank 64. The cache
  itself does not fit.
- `svd_r64` (9,191,424 B) and `palu_full_50` (8,388,608 B) fail on an **8–9 MiB** buffer instead —
  8,388,608 B is exactly the `[32, 4, 256, 128]` bf16 K-reconstruction scratch. Those two rows get
  most of the way to a 16k cache and then die on the reconstruction path's own buffers. The
  per-step reconstruction is a capacity cost as well as a latency cost, and stage 2 removes both.

### (d) Speed: V-only compression is free, K reconstruction is not

**V-only compression costs nothing.** Since Task 12, a row whose `r_k == head_dim` takes the stock K
path — stock decode RoPE, K written straight to a full-width cache, no `latent @ U_k` matmul — and
only V is stored as a latent. `svd_rk128_rv64` decodes in **38.8 / 52.1 / 69.9 ms** p50 at 1k/4k/8k
(min 38.7 / 52.0 / 69.2) against stock **38.1 / 55.5 / OOM** (min 38.0 / 55.4). It is within noise of
stock at 1k, **6 % faster** at 4k (the V cache it reads is 25 % smaller), and it runs at 8k where
stock does not allocate at all. Attention-only minima tell the same story: **1.52 / 1.27 / 1.85 ms**
against stock **0.81 / 1.31 / 2.07**.

**Rows that reconstruct K pay 2.3–9x.** Whole decode step, minima, against stock at the same context:

| context | stock | `svd_r64` | `svd_r96` | `palu_full_50` | `palu_full_70` |
|---|---|---|---|---|---|
| 1024 | 38.0 | 92.0 (2.4x) | 100.4 (2.6x) | 88.5 (2.3x) | 90.2 (2.4x) |
| 4096 | 55.4 | 265.0 (4.8x) | 282.6 (5.1x) | 265.3 (4.8x) | 262.8 (4.7x) |
| 8192 | OOM | 483.9 | 505.5 | 488.5 | 481.5 |

At 8192 stock does not allocate; the Palu rows' 482–506 ms is ~8.7–9.1x the stock **4096** step.
The cost is the attention block and nothing else: 32 x the attention-only minimum reproduces the
whole-step minimum almost exactly for every reconstructing row at 8k — `svd_r64` 32 x 15.05 = 481.6
vs 483.9 measured, `palu_full_50` 32 x 15.26 = 488.5 vs 488.5, `svd_r96` 32 x 15.72 = 503.1 vs
505.5 — whereas for stock at 1k the attention block is only 32 x 0.81 = 25.8 ms of a 38.0 ms step.
It also grows linearly with context (2.5 → 8.2 → 15.0 ms for `svd_r64`) and is nearly independent of
rank, because what it costs is the reconstruction *output* — a `[32, 4, S, 128]` scratch write plus
a RoPE rotation over the whole window, every step — not the rank of the latent matmul.
**This is exactly the cost stage 2's fused kernel removes, and the attention-only column is its
baseline.**

One caveat on the attention-only column: the bench builds layer 0 only, and layer 0 of *both*
calibrated dumps has the same ranks (32 / 128), so `palu_full_50` and `palu_full_70` measure
identical work. They differ by up to 2x at 1k (min 2.45 vs 4.82 ms) and 32 % at 4k. That spread is
the run-to-run repeatability of this microbenchmark, and no difference smaller than it should be
read as a difference between rows.

**Prefill is unaffected.** TTFT p50 spans 439.7–447.9 ms at 2048 tokens (1.9 % across all seven
rows) and 2107.0–2123.1 ms at 8192 (0.8 %), with no ordering that separates stock from Palu. Prefill
reconstructs K and V in full and then runs ordinary attention, so this is expected.

### (e) Samples

The generated samples above (greedy, 48 tokens, batch 1) track the perplexities: `baseline` is
ordinary text; **`palu_full_70` is coherent and on-topic** English; **`palu_full_50` is grammatical
but degraded**, drifting into repetition ("a 3D 3D 3D …"); and both uncalibrated SVD rows loop
immediately, `svd_r96` echoing the prompt verbatim and `svd_r64` emitting single repeated tokens.

## 3. Notes from the port

- **No fallback was needed for the MLA decode op.** `flash_multi_latent_attention_decode` accepted
  the GQA configuration (16 query heads / 4 KV heads per chip) with a **separate** V tensor of head
  dim `r_v`, so V is consumed directly from the latent cache and never reconstructed at decode. The
  spec's fallback (reconstruct V per step, stock `scaled_dot_product_attention_decode`) is unused.
- **bf16 latent caches do not help.** Prefill never reads the latent cache (it reconstructs in
  flight), so bf16 latents cannot change the prefill PCC, and decode teacher-forced agreement moved
  by one token. The `r64` fidelity gap (prefill logit PCC 0.963 against the fp32 CPU low-rank
  reference, vs 0.999 for stock against its own) lives in the **reconstruction matmul** — bf16/HiFi2
  `latent @ U_k` plus bfp8 requantisation. The lever is matmul fidelity (HiFi4 / fp32 accumulate),
  not cache dtype. The spec's latent-dtype fallback is struck.
- **RoPE-table deallocation at full context.** When the reconstruction window equals the cache
  length, `ttnn.slice` returns the *input tensor itself*; the decode path was deallocating the
  module's persistent cos/sin tables through that alias, and every later decode step failed. Fixed
  with a regression test (Task 9).
- **Prefill hidden-state readback must concatenate both chips.** The residual is column-sharded over
  the mesh, so reading chip 0 alone silently returns half the hidden state; the harness uses
  `model.concat_host_output` (Task 7 review, Critical).
- **Polling `tt-smi` wakes the board**, after which the device-idle gate reports busy for minutes.
  Device runs must be launched directly and retried with a long backoff, never pre-polled.
- **Palu upstream hard-codes 2048 Fisher samples** — both `rank_search.py` call sites pass a literal
  `2048` and silently ignore `--n_fisher_calib_samples`. At 66 s/sample in fp32 on this host that is
  a 24–38 h Fisher stage instead of ~35 min for the recipe's 32 samples. Patched.
- **transformers 5.x needed `position_embeddings`** plumbed into Palu's whitening loop, which
  otherwise crashes on the 5.x attention signature.
- **The whitening matrices of layers 0–1 must be inverted in float64.** Their condition numbers are
  ~1e16–1e18; inverting in fp32 destroys the factorisation — full-rank reconstruction error 47 % and
  235 % for those two layers, and a device perplexity of **2397** for the first calibrated dump. In
  float64 the full-rank reconstruction is exact to 1e-9 (`scripts/patch_palu_cpu.sh`).
- **ttnn's weight cache is keyed by name/shape/dtype, never content.** Two dumps with the same
  per-layer ranks shared cache entries, so the re-generated ratio-0.5 dump kept loading the broken
  dump's tensors and reproduced its perplexity bit-for-bit (2397.3228530751553 twice). Cache names
  now carry a **weight-set id** (dump basename + a hash of `config.json` and each shard's
  name/size/mtime) and a **converter version** (`CONVERT_VERSION`, bumped whenever a tensor's
  content changes under an unchanged name). Known limitation: the id uses size and mtime rather than
  content, so regenerating a dump in place within the same clock tick, at identical sizes, could
  still collide.
- **The fast-V path must collapse full-rank V into the QKV weight.** When `r_v == head_dim`,
  prefill feeds the V block of the QKV output straight to SDPA and the cache stores it as V — which
  is only correct if `U_v == I`. That holds for the identity factorisation (so every identity test
  passed and hid the bug) but **not** for a genuine full-rank SVD or whitened factorisation, which
  is what both calibrated dumps have in most layers. The converter now emits `U_v @ VT_v` as the V
  block with `u_v = I` and `wo_fused = wo` on that path. Before the fix the mixed configuration
  `svd_rk32_rv128` scored prefill PCC **0.0498** and the calibrated rows read **2433** and **3399**
  on device against a CPU reference of ~9.5; after it, 0.9996 and 12.93 / 9.03.

## 4. Deviations from the stage 1 spec

All of these are now recorded in
`docs/superpowers/specs/2026-09-09-palu-tt-stage1-design.md`:

- **§4**: the compressed weights are a *delta* file (`palu_attn.safetensors` + `config.json`), not a
  full HF dump; `wo_fused` is always 4096 x 4096, zero-padded per query-head block.
- **§5**: `set_recon_len` rounds `S` to 256, not to the 32-element tile (rounding to 32 changes the
  decode op shapes every 32 tokens and thrashes the program cache). The "Latent dtype" risk and its
  bf16 fallback are replaced by the measured finding above. Two **full-rank fast paths** are added:
  at `r_k == head_dim` the stock K path is used (no reconstruction, no `u_k` matmul), and at
  `r_v == head_dim` the V factorisation is collapsed into the QKV weight so `u_v = I` — the
  invariant whose absence produced the 2433/3399 perplexities.
- **§7**: the acceptance bars actually used are identity-vs-stock prefill logit PCC ≥ 0.999 with
  32/32 identical greedy tokens (measured 0.9994, and bit-identical since Task 12), and for `r64`
  logit PCC ≥ 0.95 against the **fp32 CPU low-rank reference** with teacher-forced token agreement
  ≥ 0.85 (measured 0.963 and 0.906; the stock control 0.999 and 0.969). The originally written 0.99
  PCC and 0.75 *free-running* greedy match were both wrong: 0.99 is unreachable even for stock
  against an fp32 reference at bfp8 weights, and free-running greedy diverges after the first
  differing token, so it measures divergence time rather than per-step fidelity (stock scores 0.19
  on it). The device attention tests also cover the mixed `rk32_rv128` configuration, which is the
  only one that exercises reconstruct-K together with fast-V.
- **§8**: the rows are baseline, identity, `r96`, `r64`, `rk128_rv64`, `palu_full_50` and
  `palu_full_70`; contexts are 1k/4k/8k plus the max-context probe (16k does not allocate at batch
  32 for any row).
- **§9**: the V-only latency criterion is restated in terms of the measured result, and a
  calibrated-recipe criterion is added. Both are met.

## 5. Pending / next steps

1. **Stage 2 — a fused K-reconstruction kernel.** Reconstruction is 95–100 % of the Palu decode
   step at 4k and 8k and grows linearly with context. The attention-only column in this document is
   its baseline; the target is the `svd_rk128_rv64` row, which shows what the step costs when K is
   not reconstructed.
2. **Group size > 1 (G-LRD).** We implement group size 1 (per-head) because the MLA decode op needs
   K and V to have the same head count and per-head latents shard across the two chips exactly like
   the original KV heads. The paper's medium-grained variant is worth 10.11 against 12.38 at the
   same 50 % budget — a larger accuracy gain than anything else on this list, and it needs a kernel
   that can index V by group.
3. **Paged cache for vLLM (stage 3).** Per-step reconstruction over a paged pool would reconstruct
   the whole pool, so paging waits for the stage 2 kernel.
4. **HiFi4 / fp32 accumulate on the two reconstruction matmuls**, if tighter fidelity is wanted.
   That is where the `r64` PCC gap lives (0.963 vs 0.999), and it is the only fidelity lever
   identified that is not a rank change.
